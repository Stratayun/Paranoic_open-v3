# Paranoic v2.1 — правила Codex

**Единый план:** [ROADMAP.md](ROADMAP.md). **Размещение новых файлов:** [docs/REPOSITORY_LAYOUT.md](docs/REPOSITORY_LAYOUT.md) (только схема каталогов; не вторая карта задач). **Задача:** новая реализация с нуля, Rust-first. UI — Kotlin Multiplatform/Compose; Rust↔Kotlin — UniFFI/Gobley или технически оправданный FFI. Android и Windows. Облака: Google Drive, OneDrive, pCloud, WebDAV (Nextcloud и др.) и собственный Rust-сервер WebDAV `paranoic-server` (решение владельца пересмотрено 2026-11-12). Без Go/Flutter в новой архитектуре, если владелец не пересмотрит решение.

1. **Главный режим — КОД.** Выполняй назначенный крупный блок последовательно; реализуй функциональность и минимальный UI при необходимости. Не отвлекайся на тесты, сборки, тестовые workflow, ревизии всей архитектуры, повторные проверки и косметические улучшения. Не запускай CI вручную и не добавляй автоматические тестовые триггеры без отдельной просьбы.
2. **Сначала закрыть кодовые дыры всех блоков; общие проверки — отдельным этапом.** Завершённые результаты не обнулять и повторно не гонять без причины. Во время закрытия дыр допустим маленький тест только затронутого файла, если без него исправление нельзя считать безопасным; полные прогоны блока — нет. **Большая проверка только по явной команде владельца:** `ПРОВЕРИТЬ БЛОК N` или эквивалентной однозначной команде. Только тогда запускай релевантные тесты/сборки/проверки безопасности для **всего выбранного крупного блока**, исправляй проблемы и повторяй нужные проверки. Не проверяй весь репозиторий без явного запроса. Если граница блока не завершена, сообщи об этом, не ставь статус «проверено».
3. **Пиши прямо в `main`.** Каждую законченную порцию кода сохраняй коммитом в `main`; проверяй актуальность branch head перед записью. Не используй force push, не теряй чужой код. Владелец скачивает полное текущее состояние как ZIP. `main` может содержать **непроверенный** код — не выдавай его за стабильный релиз.
4. **Отмечай факты, а не намерения.** `ROADMAP.md` — короткая карта (решение владельца 25.11): «Что есть» со статусами ✅ (проверено владельцем на устройстве) / 🟡 (код в `main`, не проверен) / ⏳ (частично) / — (нет), «В работе», «Дальше», «Решения владельца». Подробности открытых работ — в [PLAN.md](PLAN.md), остальное — в сообщении коммита. Сделанное и устаревшее из PLAN, problems и tests удалять: история — в git. Проблемы — в [docs/roadmap/problems.md](docs/roadmap/problems.md) (новая — следующим номером; исправлена — статус и SHA; исправлена и проверена — удалить строку). Тесты — в [docs/roadmap/tests.md](docs/roadmap/tests.md) (только фактически выполненные прогоны). Заглушка/макет — не плюс.
5. **Не переписывай карту.** Не меняй порядок и объём блоков, не создавай новые ROADMAP/STATUS/параллельные планы без явного решения владельца. Дополняй новые функции через компактные интерфейсы/адаптеры по мере их востребованности; не строй гипотетическую инфраструктуру.
6. **Береги данные при реализации.** Не публикуй секреты; не удаляй исходник до подтверждённого результата; не делай автоматическое повторение неопределённой записи. Защищённые заметки (1.9) изолированы от File Manager и Cloud и не синхронизируются; Clear стирает только заметки уничтожением их ключей и оставляет пустой раздел для повторного использования. Не обещай абсолютного стирания внешних резервных копий. Даже без запуска тестов нельзя сознательно игнорировать известную проблему безопасности или потерю данных. Записывай такие блокеры кратко и конкретно.
7. **Не зацикливай проверки.** Перед разрешённым прогоном фиксируются SHA и граница проверки. Параллельные проверки — только на изолированных checkout/данных/build-каталогах. После прерывания, тайм-аута или ошибки сначала записать исход и убедиться, что процесс освободил ресурсы; следующий пересекающийся прогон не запускать до этого. Автоматически повторять тот же прогон запрещено; повтор — только после конкретного исправления либо устранения причины сбоя. После проверки блока переходи дальше. Возвращайся к старому блоку только по реальному дефекту, зависимости, риску безопасности/целостности или команде владельца; тогда проверяй только затронутые части, если нет основания для более широкого прогона.
8. **Отчитывайся коротко:** блок/подпункт, что написано, `Код +/—`, `UI +/—/н/п`, `Проверка +/—`, SHA в `main`, следующий незакрытый пункт. Не утверждай прохождение тестов, устройства или платформы без фактических результатов.

9. **Распределение работ — у владельца.** Отдельной доски «кто чем занят» нет (решение 25.11); перед правкой общего файла сверяй актуальный `main`.

**Строгая граница ответственности (Opus / Sol).** Разделение по владельцу исходного слоя, не по названиям функциональных задач:

- **Opus — Rust:** `crates/**`, Rust-сторона UniFFI/FFI, форматы, файлы, криптография, безопасность, облако, ядро и Rust-тесты. Не редактирует Kotlin/Compose и платформенные Kotlin-адаптеры без отдельного согласованного поручения.
- **Sol — Kotlin:** `ui/**` (Compose `commonMain`, Kotlin Android/Desktop/JVM, `CoreGateway` / `NativeCoreGateway`, UI-состояние, навигация, визуал и Kotlin-тесты). Не редактирует Rust-код без отдельного согласованного поручения. Kotlin-адаптеры ОС остаются у Sol, но их безопасность и файловые гарантии согласуются с Opus.
- **Общая граница:** [CONTRACTS.md](docs/architecture/CONTRACTS.md), UniFFI-DTO/методы/ошибки, прогресс, отмена, безопасный lifecycle. Изменение интерфейса: (1) согласовать контракт и совместимость, (2) Opus меняет Rust API, (3) Sol подключает Kotlin gateway и UI, (4) интеграцию проверяют только в разрешённом объёме. Пока Rust-метод не готов, Sol может работать через Fake Gateway; заглушка не означает готовую интеграцию.
- **Пересечения и координация:** работу распределяет владелец. Общие файлы `AGENTS.md`, `ROADMAP.md`, `PLAN.md`, `CONTRACTS.md` и настройки сборки изменять согласованно, сверяя актуальный `main`. Под задачу `Opus / Sol` ответственность делится по слоям, а не назначается целиком обоим. Спор о контракте / нарушении границы — на решение владельца.
- **Ограничения:** нет смены стека и переработки архитектуры; Rust-first + Kotlin/Compose остаются. Это снижает пересечения, но не отменяет зависимостей, интеграционных ошибок и необходимость проверок.

**Технические договорённости** (контракты Rust ↔ мост ↔ Kotlin): [docs/architecture/CONTRACTS.md](docs/architecture/CONTRACTS.md).

**Порядок задач:** 1. Ядро и файлы → 2. Архивы и документы → 3. Облако → 4. Интерфейс и платформы. Простой UI допускается по мере потребности; визуальный редизайн позже. Новый пункт в карте не инициирует тесты сам по себе.
