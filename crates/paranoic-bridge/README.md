# New Core bridge — 4.2

One UniFFI 0.29.4 ABI, generated Kotlin/JNA bindings for Android and Windows.
No old JNI/native runtime is used. Both entry points construct NativeRuntime.
The generator source is committed; generated Kotlin and native binaries are
build outputs, generated by tools/build/native.py when a build is authorized.

NativeRuntime owns the current Core worker. Storage IDs are UUIDs. New grants
are registered append-only after the journal binding is committed, without
restarting Core. Rebinding an existing UUID is rejected. Host stores persist a
candidate grant UUID before registration, so an uncertain reply never creates
a new identity automatically. Native writes use Core::submit_with_id; the UI
does not retry uncertain writes or equate submission with completion.

Android callbacks are OS grant traversal and descriptor IO; Rust owns every
policy. SAF grants with persisted write permission accept create-new writes:
bytes go to a hidden ".paranoic-<job>" document, publish renames it to the
target name, and because providers pick a unique name when the target exists,
a differing actual name means "taken" — our own document is deleted and
AlreadyExists returned. Nothing existing is overwritten. Residual race: a
provider that overwrites on rename while another app creates the same name.
SAF moves are not offered (no atomic no-replace); folder deletion checks
emptiness first (deleteDocument is recursive). Pipe-backed documents (cloud
providers) are readable sequentially; random access on them is Unsupported.
The host caches path→document resolution, re-verified by display name.

Listings for display (`list`) omit entries with non-portable or duplicate
names and return their count (`skipped`) instead of failing the folder; Core
operations keep the strict listing, so copies/deletes never skip silently.

Windows external grants are capability-confined, read-only, with handle-based
volume/file identity via cap-fs-ext. App-private Files permit create/copy via
hard-link create-new publication. The host-created user profile directory is
required to have a private Windows ACL. Arbitrary selected directories never
receive this privilege. ReFS 128-bit IDs, network shares, filesystems lacking
hard links, directory moves, replacement and power-loss directory durability
are not claimed. The adapter reports unsupported capabilities instead.
Windows staging closes file and directory handles before cleanup.

NativeReader pins metadata on the opened object and checks it around bounded
random-access reads. Read size <= 1 MiB. Image decoding is serialized, input <=
32 MiB, decoded RGBA <= 64 MiB; thumbnails/preview are <= 1024 pixels per side.
No plaintext media spool is created by the bridge.
Only Files storages are registered as spaces. Encrypted folders (format 1.8) are opened by `vault_*` handles; protected notes (1.9) are reachable only through `notes_*` and never appear as a space.

PDF: PDFium is never loaded in the app process. `pdf_page`/`pdf_search` use
`paranoic_documents::pdf_client::PdfSession`, which starts the separate
`paranoic-pdf-worker` executable (Android: `libparanoic_pdf_worker.so` in
nativeLibraryDir; desktop: next to the app resources) with a cleared
environment, sends the PDF once over a pipe and receives bounded PNG/search
replies with a 30 s deadline; timeout/crash/protocol error kills the worker.
One session per open document (parsed once), restarted if the file changes.
The worker runs with the app's UID; an Android isolatedProcess service is a
further hardening step. The worker binds a trusted absolute Pdfium path
(pdfium-render 0.9.5). The build bundles Pdfium ABI 8125 for each
architecture (tools/build/native.py, pinned and SHA-256-checked); it is never
downloaded at runtime. No V8/XFA feature is enabled.
Input <= 64 MiB, output <= 4096x4096, pages <= 20000. Search scans <=16 pages
per request and returns a continuation. No OCR/password/forms support.
The worker confines itself (seccomp + rlimits on Linux/Android, job object +
Low integrity on Windows). Android isolatedProcess remains open (ROADMAP У-4).

Verification status of the bridge is recorded only in the root ROADMAP.
