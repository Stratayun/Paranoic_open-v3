# Core API

Ядро блока 1. Регрессионные тесты проходят на Linux x86_64, Rust 1.87.0
(2026-11-12, evidence в ROADMAP); зависимости зафиксированы в `Cargo.lock`.
Аудит зависимостей и проверка на Android/Windows не выполнялись. Кода UI и FFI здесь нет.

## Границы модулей

- `paranoic-core`: модели, ошибки, валидация, capability-контракт хранилища,
  один поток исполнения, ограниченная очередь и SQLite-журнал.
- `paranoic-local`: native-каталоги через `cap-std`. Только выдача корневого
  доступа использует ambient authority. Операции работают через directory handles.
- Будущие Android SAF, Windows и облачные адаптеры реализуют `Storage`.
  Если backend не обеспечивает контракт, он возвращает `Unsupported`.

`Core` не зависит от Tokio, UI, сети или платформенного SDK. `StorageRegistry`
неизменяем после запуска. `StorageId` сохраняется хостом вместе с разрешением;
журнал запоминает digest идентичности корня и запрещает подменять корень под
существующим ID. Unix-адаптер использует device/inode. Отсутствующий grant не
подменяется доступом к другому каталогу.

## Подключение хостом

1. Получить разрешение ОС и открыть `LocalStorage::open(id, root, access)`.
2. Передать адаптер в `StorageRegistry::register(Arc::new(storage))`.
3. Открыть `Core::open(private_state_directory, CoreConfig::default(), registry)`.
4. Вызывать `list`/`metadata`/`open_read`, отправлять `Operation` через `submit_with_id`.
5. Читать `job`/`recent_jobs`/`jobs`, запрашивать `cancel`. UI локализует `ErrorCode`.
6. При завершении вызвать `request_shutdown`, затем `close` вне UI-потока.

Хост заранее сохраняет UUID задания, если нужна безопасная повторная отправка
после потери ответа. Один ID + тот же запрос возвращают существующее задание.
Один ID + другой запрос отклоняются. История ID не очищается автоматически:
это сохраняет защиту от повторного исполнения. Хранилище журнала поэтому растёт
с историей, хотя число активных заданий и объём одного snapshot ограничены.

State directory должен быть отдельным приватным каталогом приложения на локальной
файловой системе, поддерживающей SQLite WAL и файловые блокировки. Он не должен
находиться внутри пользовательского grant или Private Vault. На Unix проверяется
владелец и устанавливаются права 0700. Один OS lock защищает его от второго Core.
Отдельные Core с разными state directory не сериализуют операции друг друга.

Проверено на Linux x86_64 (2026-11-12): конфликты KeepBoth/Replace, копии с
сохранением времени, перенос файла и папки между хранилищами. Android/Windows — нет.

Пути относительные и проверяются также при десериализации журнала. Запрещены
`..`, абсолютные/UNC/drive-пути, ADS, управляющие символы, Windows device names
и внутренний префикс `.paranoic-`. Корни нельзя удалять или перемещать.
В этой версии непреносимые или не-UTF-8 имена дают ошибку, а не изменяются
неявно. Превышение лимита каталога также даёт ошибку вместо неполного списка.

Native-копия создаёт приватный каталог `.paranoic-<job UUID>` рядом с назначением,
пишет `payload`, делает file sync, затем публикует hard link без перезаписи.
Файловые системы без hard links, в том числе некоторые съёмные носители,
пока не поддерживают этот способ публикации. Небезопасного fallback нет.
`Fail` и `Skip` учитывают как существующее назначение, так и конфликт в момент
атомарной публикации. Исходник при копии никогда не удаляется.

`KeepBoth` выбирает первое свободное имя `имя (N).расширение` (N до 9999; для
папок номер добавляется к полному имени). Выбранный путь записывается в журнал
(`active_entry`) до первой записи и возвращается в `OperationResult::target`.
Если имя занимают между выбором и публикацией, публикация без замены даёт ошибку.
`Replace` работает только «файл поверх файла»: новый файл полностью пишется в
staging, старый переносится в скрытый `.pnc-replaced-<job>` (путь в журнале),
проверяется, что он не изменился с момента осмотра (иначе возвращается на место,
SourceChanged), затем публикуется новый и удаляется старый. Если публикация не
удалась, старый возвращается; если вернуть или удалить его не удалось —
`NeedsAttention`, старая версия остаётся в скрытом файле. Папки не заменяются и не сливаются.

Время изменения переносится для файлов (на staging-дескрипторе до публикации) и
папок (после копирования содержимого, глубже — раньше). Ошибка установки времени
игнорируется: копия важнее метаданных.

На Linux/Android перенос использует `renameat2(NOREPLACE)`; фактическая поддержка
зависит от ОС и файловой системы. Межфайловый перенос не заменяется копией
с последующим удалением. На Unix изменения каталогов синхронизируются; ошибка
синхронизации после мутации оставляет неопределённый результат в журнале.

Windows: привязка к FileId, staging через временную папку с ACL «только
владелец» и перемещение без замены — `crates/paranoic-windows`. Android SAF
не является native-путём и обслуживается отдельным адаптером моста.
Статус проверки платформ — только в корневом ROADMAP.

Копирование ограничивает память одним буфером, контролирует исходный размер
и метаданные открытого файла. BLAKE3 в результате описывает записанный поток;
это не повторное чтение назначения. Метаданные не обеспечивают snapshot
от параллельного внешнего редактирования: для этого нужен отдельный контракт
снимка/версии backend. Native grant и внутренний staging защищены от выхода
по путям, но не являются границей безопасности от процесса с тем же OS-пользователем.

## Журнал, отмена и сбои

SQLite использует WAL, `synchronous=FULL`, версию схемы и application ID.
Незнакомую или более новую схему ядро не обнуляет. Сначала фиксируется
`Running`, затем intent `effects_started`, и только потом вызывается мутация.
Результат и прогресс фиксируются транзакционно. Если итог записать нельзя,
worker останавливается; `health()` сообщает ошибку.

При следующем запуске:

- `Queued` продолжают ждать исполнения.
- `Running` без intent можно вернуть в очередь: побочных эффектов ещё не было.
- `Running` с intent становится `NeedsAttention`; автоматического повтора нет.
- Успешные и завершённые задания не переисполняются.

Отмена очереди немедленна. Копирование замечает её между буферами и явно
удаляет staging до `Cancelled`. Если очистку нельзя подтвердить, остаётся
`NeedsAttention`. После точки публикации поздняя отмена не откатывает результат.
Короткие атомарные операции не прерываются посередине. Shutdown прекращает приём
заданий; очередь сохраняется, текущая копия получает запрос остановки.
Зависший системный I/O не имеет принудительного таймаута; `close` может ждать его.

Для `NeedsAttention` хост должен показать операцию, source/target, ошибку и ID.
`jobs(0, Some(JobState::NeedsAttention), limit)` начинает выборку всех таких
заданий; `next_cursor` продолжает её без ограничения последней тысячей записей.
Каждая страница — отдельный snapshot; при изменении состояний выборку начинают
заново, если нужен актуальный список целиком.
Нужно сопоставить источник, назначение и `.paranoic-<ID>/payload`, прежде чем
принимать решение. Эта версия сохраняет неизвестность и артефакты после crash;
автоматической очистки, повторной записи и UI разрешения неоднозначности нет.
Даже видимое назначение не доказывает, что оно принадлежит именно этому заданию.

Запрет регистрации `StorageDomain::PrivateVault` задаёт только границу общего
файлового API (прежний Private Vault заменён форматом 1.8, который работает поверх
обычных Files). Это не замена шифрованию и системной изоляции.

## Рекурсивная копия (продолжение 1.2)

`Operation::CopyDirectory` исполняется в общей очереди. До записи выполняется
ограниченный обход и проверка всех путей назначения. Копия создаёт новый каталог;
`Skip` пропускает целиком существующее назначение, слияния каталогов нет.
Прогресс считает суммарные байты файлов и сохраняется в том же журнале.
Каждый файл публикуется отдельно без замены. Всё дерево не является атомарной
транзакцией: отмена/ошибка после создания корня оставляет частичное назначение
для ручного разбора, без автоматического повтора или рекурсивной очистки.
Исходник никогда не удаляется. Проверка метаданных обнаруживает часть внешних
изменений, но не заменяет snapshot. Алиасы через разные вложенные grants
не всегда определяются как перекрытие; обход фиксируется до записи, повторного
обхода создаваемой копии нет. Актуальный статус 1.2 — в таблице выше.

## Удаление дерева

`DeleteDirectory` сначала строит ограниченный список, затем удаляет его в обратном
порядке. Новые дочерние элементы не подхватываются: удаление непустой папки даёт
ошибку. Символические ссылки и специальные объекты отклоняются. На Unix каждый
компонент каталога открывается через `openat(NO FOLLOW)` и удерживаемый дескриптор.
Отмена после начала удаления означает `NeedsAttention`, а не откат; автоматического
повтора после crash нет. Прогресс хранит байты удалённых файлов. Это окончательное
удаление, не корзина. Метаданные не являются атомарным условием unlink: одновременно
изменяемые другим процессом обычные файлы могут быть подменены между проверкой
и удалением. Для такой среды потребуется отдельный backend с versioned delete
или изоляция дерева; текущий native API не обещает snapshot-гарантии.

Журнал дерева также хранит `entries_done`, `entries_total` и `active_entry`.
Текущий путь фиксируется до обработки объекта и сохраняется при неопределённом
результате. Завершение отдельного объекта фиксируется после его обработки.
При crash счётчик может отставать от реального результата: это подсказка для
разбора, а не разрешение повторить удаление. Поля имеют serde-default, поэтому
старые записи читаются без пересоздания базы. Пустые файлы и папки учитываются
в счётчике объектов, даже когда байтовый прогресс равен нулю.

## Подтверждённая копия и межхранилищный перенос

`CopyVerified` публикует файл без замены, повторно читает назначение и сравнивает
размер и BLAKE3 записанного потока. Журнал сохраняет фазу и digest до публикации,
затем отдельно отмечает успешное повторное чтение. Это историческое подтверждение,
не гарантия неизменности файла после операции. Ошибка или отмена после публикации
оставляют назначение и `NeedsAttention`, исходник не удаляется.

`MoveFileAcross` использует тот же поток, но требует от адаптеров двух дополнительных
гарантий: неизменяемой версии исходника с атомарным условным удалением и защищённого
назначения, которое нельзя изменить или удалить до снятия lease. Удаление начинается
только после сохранённого `Verified`; intent `RemovingSource` записывается до вызова
адаптера, `SourceRemoved` — после. Неизвестный результат никогда не переигрывается.
Локальный Unix-адаптер (2026-11-12) реализует обе гарантии как «проверка
непосредственно перед действием», а не как блокировку: lease исходника запоминает
dev/ino, размер, mtime и ctime открытого файла; `remove()` удаляет имя, только если
оно всё ещё указывает на тот же неизменённый объект. Назначение после сверки
проверяется так же (`still_published`) прямо перед удалением исходника; при
расхождении исходник остаётся. Остаточный риск: подмена имени в микросекундном
окне между последней проверкой и unlink и запись процессом, открывшим файл раньше, —
как у обычного перемещения в файловом менеджере.

`MoveDirectoryAcross` копирует дерево (без замены), читает назад каждый файл и
сверяет BLAKE3, затем удаляет исходные объекты в обратном порядке: файлы — только
с неизменными метаданными, папки — только пустые. Любая ошибка после копии даёт
`NeedsAttention`: оба дерева остаются для разбора, повторного запуска нет.

## Явное принятие результата создания Cryptomator

Для `PublishTree` со статусом `NeedsAttention` добавлен отдельный цикл принятия
результата. `inspect_prepared_tree(id, cancelled)` даёт только текущее наблюдение.
После явного решения в интерфейсе хост вызывает
`accept_prepared_tree(id, cancelled)`: ядро самостоятельно повторяет чтение всего
подготовленного дерева, проверяет привязку storage grant и только при `Matches`
сохраняет `JobRecord.bootstrap_acceptance` в транзакции SQLite. Передавать ранее
полученный `Matches` вместо свежего чтения нельзя. Отсутствующее/изменённое дерево,
ошибка чтения или отмена до фиксации не создают подтверждение.

Запись содержит время фиксации, BLAKE3 исходного запроса с отдельным контекстом и
версионированным бинарным представлением, digest привязки хранилища, число файлов
и байтов. Это контроль согласованности в доверенном журнале, не цифровая подпись.
При чтении журнала запись сопоставляется с исходной операцией и её состоянием.
Старые записи без этого поля читаются как неподтверждённые; таблицы не пересоздаются.

Исходные `state`, `error`, `result` и прогресс не переписываются. В частности,
`NeedsAttention` не превращается в `Succeeded`: принятие текущих байтов не
доказывает успешный fsync во время первоначальной попытки. `job()` и `jobs()`
показывают историю полностью. `unacknowledged_attention(after, limit)` выдаёт
страницами задания без записанного решения; это очередь решений, а не список
всех оставшихся временных артефактов. При обновлении экрана обход начинается с
нулевого курсора; страницы не образуют единый снимок.

Повторный вызов принятия для того же ID возвращает первоначальную запись, даже
если после её фиксации хранилище изменилось. Для нового наблюдения используется
`inspect_prepared_tree`. При потере ответа или неопределённой ошибке записи нужно
прочитать `job(id)`, затем при необходимости повторить принятие того же ID;
не создавать заменяющую файловую операцию. Одновременные вызовы сохраняют одно
подтверждение. Поздняя отмена не откатывает уже зафиксированную транзакцию.

Принятие не блокирует внешние изменения дерева, не доказывает долговечность
назначения, не очищает staging и не разрешает повторную публикацию/удаление.
Решение хоста относится только к наблюдаемому содержимому. UI/FFI для этого
действия, автоматическая очистка артефактов и подтверждение результатов на
устройствах ещё не реализованы.

## Связанная публикация каталога формата

`PublishLinkedTrees` хранит две ограниченные группы файлов для непересекающихся
путей одного storage grant. На каждую группу действуют лимиты `PublishTree`:
до 32 файлов, 64 KiB и восьми компонентов относительного пути. Валидация путей,
ресурсных лимитов и возможностей backend выполняется до записи. Это контракт
упорядоченной публикации для Cryptomator, не распределённая транзакция.

Ядро сначала публикует и читает обратно группу `data`, затем публикует и читает
`target`, после чего повторно наблюдает `data`. Существующие назначения не
заменяются. `entries_done` считает подтверждённые этапы из двух, `active_entry`
сохраняет текущее назначение. Эти поля могут отставать от файловой системы при
сбое; они не разрешают повторять запись. После первой публикации отмена оставляет
`NeedsAttention`, даже если staging второго этапа удалось полностью очистить.

`inspect_linked_trees(id, cancelled)` читает сохранённый запрос терминального
задания и возвращает отдельные `data` и `entry` наблюдения. Он не повторяет запись
и не меняет статус. Ошибки чтения остаются ошибками. Два наблюдения последовательны,
не образуют снимок и не гарантируют отсутствие последующих изменений. Принятие
bootstrap через `accept_prepared_tree` по-прежнему относится только к `PublishTree`.


## Принятие результата связанной публикации

`accept_linked_trees(id, cancelled)` — отдельное явное действие хоста для
`PublishLinkedTrees` в `NeedsAttention`. Ядро читает данные, ссылку и снова данные;
все наблюдения должны совпасть с исходным запросом. Привязка grant проверяется
до/после чтения и сопоставляется с сохранённой привязкой внутри транзакции.
Кешированное наблюдение и частично совпавшее дерево не позволяют записать решение.

`linked_trees_acceptance` хранит дату фиксации, digest обеих упорядоченных групп,
привязку storage и отдельные счётчики данных/ссылки. Обе схемы принятия используют
одну транзакционную реализацию, но разные типы записей и контексты digest. Старое
бинарное представление `bootstrap_acceptance` сохранено. Декодирование проверяет
тип операции, состояние и соответствие digest/счётчиков сохранённому запросу;
старые задания читаются с отсутствующим подтверждением без пересоздания базы.

Повторный запрос возвращает первоначальное решение. После неопределённого ответа
нужно прочитать то же задание, затем при необходимости повторить принятие с тем
же ID. Новое наблюдение выполняется отдельным `inspect_linked_trees`. Отмена до
фиксации не создаёт подтверждения; завершившийся commit не откатывается поздней
отменой. Shutdown закрывает допуск перед финальной транзакцией.

`unacknowledged_attention` учитывает оба вида принятия, а `jobs()` сохраняет всю
историю с исходной ошибкой. Это завершает принятие наблюдаемого содержимого,
не восстановление отсутствующих объектов: запись одной существующей половины,
повторная публикация, удаление и очистка staging не выполняются. Снимок файловой
системы, гарантия прежнего fsync, UI/FFI и проверка на устройствах не заявляются.
