# Crypto Engine — кодовая часть 1.6

**Код 1.6 написан; UI — нет.** Регрессионные тесты блока 1 (ключи, контекст,
ревизии, блокировка, потоковое шифрование, повреждение/обрезка) проходят на Linux
x86_64, Rust 1.87.0 (2026-11-12, см. ROADMAP). Внешнего криптографического аудита
и проверки на Android/Windows нет. Код завершения API: `710da66975455ec2a7abc44d16667b026b021f8d`.

1.6 здесь охватывает Rust-движок и управление ключами. Совместимые внешние
контейнеры — 1.7; собственный формат — 1.8 (`paranoic-formats`), заметки и Clear —
1.9 (`paranoic-notes`); Keystore/DPAPI, биометрия и UI — блок 4. Статусы — в ROADMAP.

## Реализованные сценарии

- `CryptoEngine::open`: открытие приватного парольного хранилища и менеджера сессий.
- `create_key`, `key`, `keys`: создание случайного ключа, получение записи,
  постраничное перечисление до 256 записей за вызов без раскрытия ключей.
- `unlock`: парольное открытие с контролем revision, TTL и лимита сессий.
- `SessionHandle::seal/open`: шифрование и аутентификация объектов до 16 MiB.
- `SessionHandle::encrypt_stream/decrypt_stream`: большие файлы с ограниченной
  памятью, отменой и публикацией результата только после полного завершения.
- `change_password`: отзыв всех сессий, транзакционная смена текущей обёртки,
  запрет foreground/unlock до завершения изменения. После успеха или ошибки
  требуется отдельный Foreground и новое открытие по паролю.
- `export_key/import_key`: явный зашифрованный backup с отдельным паролем,
  восстановление только в отсутствующий ID, без замены существующего ключа.
- `lock_session`, `on_event`: отзыв одной/всех сессий, фон, блокировка экрана,
  suspend, foreground и окончательный shutdown.
- Автоматическое удаление просроченных неиспользуемых ключей фоновым потоком;
  защита от завершения старого KDF после события блокировки.

`CryptoEngine` не выдаёт открытые ключи. У `SessionHandle` нет unlock/замены
ключа; старый handle не оживает при открытии новой сессии. Нижележащие API
`SecretKey`, `KeySession` и `PasswordKeyring` доступны для адаптеров, но обход
менеджера означает самостоятельную ответственность хоста за их жизненный цикл.

## Криптографические форматы

Используются RustCrypto XChaCha20-Poly1305, Argon2id и OS RNG. Ключи 256-битные,
без Debug/Clone/serde; owned secrets и возвращаемый plaintext очищаются через
zeroize. Входные password/plaintext slices принадлежат вызывающему коду.

`PRNDAT01`: magic 8 байт + nonce 24 байта + AEAD ciphertext/tag. Обязательный
внешний контекст и его длина входят в authenticated data вместе с magic.
Контекст ограничен 4096 байт и должен однозначно связывать домен, ID объекта,
тип и поколение. Простое склеивание произвольных строк не подходит.

`PRNKEY01`: magic 8 + соль 16 + nonce 24 + ciphertext/tag 48, всего 96 байт.
Argon2id v1.3: 64 MiB, 3 прохода, 1 lane, выход 32 байта. Параметры фиксированы
версией, не выбираются из непроверенного файла. Соль входит в associated data.
Смена пароля меняет обёртку, не случайный data key.

`PRNBKP01`: magic 8 + исходный key ID 16 + PRNKEY01 96, всего 120 байт. Весь
заголовок backup аутентифицируется обёрткой. После восстановления ID и data key
сохраняются, локальная revision начинается с 1. Контексты зашифрованных объектов
нужно сохранить. Backup создаётся только по явному вызову, не автоматически.

`PRNSTR01`: magic 8 + случайный nonce prefix 19 + размер блока u32 LE. Используется
RustCrypto STREAM BE32 поверх XChaCha20-Poly1305. Запись: final u8 + длина
ciphertext u32 LE + ciphertext/tag. Обычные блоки plaintext имеют размер 1 MiB;
последний короче, включая пустой final при кратной длине. Header и контекст
аутентифицируются каждой записью; STREAM связывает счётчик и final-признак.
Обрыв, перестановка, неверный final и хвост после final отклоняются. Лимит
plaintext задаётся до 1 TiB. Память ограничена несколькими буферами размера блока.
Форматы требуют проверки перед объявлением стабильным внешним контрактом.

## Хранилище и публикация

`StreamSink` — временное непубличное хранилище с commit/abort и очисткой при Drop.
До успешного final/EOF расшифрованные блоки нельзя показывать или помещать
в общий кеш. Ошибка commit может означать уже опубликованный результат:
она не разрешает автоматического повтора или удаления назначения.

`PrivateDirectory` — конкретный Unix sink. Каталог уже должен существовать,
принадлежать текущему пользователю и не иметь доступа группы/остальных.
Только непрозрачные ObjectId используются как имена. Временные файлы 0600,
эксклюзивное создание, file sync, hard link без замены, directory sync,
удаление временного файла. Нужна файловая система с hard links/directory sync.
Windows для данного адаптера возвращает Unsupported. Этот каталог никогда
не должен быть Files/Cloud grant; хост защищает и его родительские каталоги.

Порядок работы: сохранить выбранный ObjectId, получить `stage(id)`, передать
sink в потоковую операцию, после Ok читать `open_object(id)`. Удаление объекта
выполняется отдельным явным `remove_object`, не автоматически при ошибке.
После crash могут остаться `.pending-*`; при расшифровке это plaintext внутри
приватного каталога. Sink не является механизмом временных данных Vault/Quick
Lock без дополнительного recovery и исключения backup на уровне приложения.

`PasswordKeyring` хранит только парольные обёртки в SQLite WAL/FULL, проверяет
версию/application ID и удерживает process lock. Незнакомая БД не обнуляется.
Смена пароля проверяет revision и заменяет запись транзакционно. После потери
ответа надо получить актуальную revision и определить результат, не повторять
запись вслепую. Это парольное хранилище, не аппаратный OS keystore.

## Сессии и ошибки

Доступ к ключу сериализован. Запрос блокировки запрещает новые обращения;
потоки замечают его на контрольных точках и вызывают abort. `lock` ожидает
завершения и удаляет ключ. Уже выданный plaintext отозвать нельзя. Системный
I/O принудительно не прерывается; commit, начавшийся до отзыва, может завершиться.

Менеджер учитывает активные сессии и незавершённые KDF. При блокировке меняется
поколение допуска: старое открытие не принимается даже после Foreground.
Обработку реальных событий должен вызывать хост. Блокирующие события и Drop
выполняются вне UI-потока; их нельзя вызывать из callback операции той же сессии,
поскольку это ожидание собственного завершения.

Неверный пароль ограничивается задержками 1, 2, 4, 8, 16, 30 секунд до нового KDF;
`password_retry_after` сообщает остаток. Используются монотонные часы, без sleep.
Лимит общий для экземпляра и охватывает unlock, change_password, backup/restore.
История ошибок сбрасывается после пяти минут без ошибки, не после успешного
входа в другой ключ. Переоткрытие экземпляра сбрасывает in-memory лимит.

## Границы безопасности

AEAD не предотвращает откат на старый аутентичный объект. Поколения объектов,
защита от rollback и удаление всех копий ключей относятся к использующему
движок формату/Vault. Старые обёртки могут оставаться в WAL, страницах, backup
и snapshots. `secure_delete` не гарантирует их уничтожение. Сохранённый backup
позволяет восстановить ключ даже после смены локального пароля.

Zeroize не гарантирует отсутствие копий в swap, дампах, регистрах и внешних
backup. Приватный каталог не защищает от другого процесса с тем же OS-пользователем.
Для полного приложения нужны системные политики, адаптеры и проверки блока 1.
